What it does, in plain English

A business-friendly walkthrough of one request.

  1. 1
    A request arrives
    Another program sends a small package: what to do (Add / Update / Delete / Inquiry), which customer, and a data payload.
  2. 2
    Open the customer master file
    If we can't open the file, we stop immediately and report a system error.
  3. 3
    Route to the right operation
    A simple switch sends the request to Add, Update, Delete, or Inquiry. Anything else is rejected as invalid.
  4. 4
    Validate & apply business rules
    For Add and Update we call the shared CUSTVAL validator, then automatically apply a 5% discount to any balance over $10,000.
  5. 5
    Persist or return data
    The customer record is written, updated, deleted, or read back to the caller depending on the request.
  6. 6
    Close cleanly
    The file is closed and a return code + message tell the caller exactly what happened.

Business rules to preserve

These are the rules our modern Java service must carry over without drift.

Customer ID is unique
An Add for an existing customer is rejected (return code 1002). Maps to a unique constraint plus an existsById precheck.
5% discount on balances > $10,000
Applied on every Add and Update, not just at inquiry time. Overflow is reported as 6001.
Money is decimal, never floating point
Balance and discount are COBOL packed decimal (COMP-3) → must become BigDecimal in Java. Never double / float.
CUSTVAL is a hard dependency
Every Add / Update synchronously validates via the shared CUSTVAL program. It must be migrated or stubbed before this service is functionally complete.
Customers have at most 3 phones
CUST-PHONES OCCURS 3 TIMES (type H / W / M) → child table / collection capped at 3 entries.
Status is a fixed set: A / I / S
Active, Inactive, Suspended — model as an enum + CHECK constraint.
