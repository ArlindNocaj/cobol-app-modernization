The starting context

What Copilot already "knew" before the operator typed anything

The repository contains a project-level .github/copilot-instructions.md that Copilot loads automatically on every turn. It encodes the project's conventions so the operator does not have to repeat them in every prompt:

Target stack
  • Java 17 (LTS) — records, sealed classes, switch expressions
  • Spring Boot 3.2, Spring Data JPA, Flyway
  • Azure SQL · MongoDB · React 18.2 + TS
  • GitHub Actions for CI/CD and batch orchestration
Migration rules baked in
  • BigDecimal for every COBOL decimal field (never double)
  • Constructor injection, @Transactional, SLF4J
  • OpenAPI / Swagger annotations on every endpoint
  • Package layout com.acme.{domain}.{layer}
  • JUnit 5 + Mockito · Testcontainers · 90% coverage target
Why this matters for the demo
None of the prompts below repeat any of these conventions. The Java code that comes out the other end — entities with BigDecimal and audit columns, a Flyway migration with snake_case, records as DTOs, exception handler mapping to HTTP — all flows from this single instruction file. Customers see the value of investing in copilot-instructions.md as a one-time set-up.

Analyze the COBOL program

Goal: structured summary the team can review before any code is touched
Analyze this COBOL program and provide a structured summary: 1. Divisions and sections 2. All CALL dependencies 3. All COPY dependencies 4. A plain-English summary of business logic

Copilot read samples/cobol/CUSTMGMT.cbl and its copybook CUST-REC.cpy, then returned a structured analysis covering all four requested dimensions. The key findings:

  • 1 external CALL — CUSTVAL for field-level validation, invoked on every Add/Update.
  • 1 COPY — CUST-REC defining the customer master record (with OCCURS 3 TIMES phones).
  • 4 transaction types dispatched from 0000-MAIN: Add / Update / Delete / Inquiry.
  • Implicit business rule: 5% discount applied automatically whenever balance > $10,000.

Convert COBOL to a Java 17 Spring Boot service

From understanding the program to a buildable Maven project
Convert this COBOL program to a Java 17 Spring Boot service. Use BigDecimal for all decimal fields. Use Java records for DTOs.

Copilot scaffolded a complete Maven module under services/customer-service/: domain entities, repository, service layer (with discount calculator and validator stub), REST controller, DTOs as Java records, global exception handler, a Flyway migration, and unit tests. The COBOL paragraph names are preserved in Javadoc so the mapping is auditable.

Run it — do the tests actually pass?

Evidence the generated code is buildable, runnable, and behaviourally correct
Can you run and test it ? does it work? do the tests work?

Copilot ran mvn test, hit one local environment issue (Mockito's inline mock maker doesn't support JDK 25 — only JDK 25 is installed on this machine, project targets 17), diagnosed and fixed it by swapping a mock for a real instance, then re-ran. After that it built and started the JAR and exercised every endpoint with curl to prove parity with the COBOL contract.

What the customer gets out of this

Why this matters, beyond one program
Captured, not hand-waved

Every business rule visible in the COBOL — uniqueness, 5%/$10K discount, validator dependency, status enumeration, phone cardinality — is encoded in the Java service and in tests that fail loudly if a future change breaks parity.

Conventions enforced once

The project-level copilot-instructions.md file is the policy boundary. Decimal precision, package layout, Flyway use, OpenAPI annotations — none of that had to be re-stated in any prompt.

Auditable mapping

Every Java class includes Javadoc citing the originating COBOL paragraph (1000-ADD-CUSTOMER, 6000-APPLY-DISCOUNT, …) so reviewers can trace any line back to source.

Reproducible

The whole walkthrough is 5 prompts. The two HTML artifacts in ./results/ embed those prompts at the top so any team member can re-run on the next program.
